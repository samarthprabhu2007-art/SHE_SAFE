WHAT THE SYSTEM DOES (unchanged) This device detects hidden/spy cameras in a room using an ESP32 (as a sensor hub) and the user's smartphone (running the app). It has two detection subsystems plus an emergency alert feature:

WIRELESS CAMERA RADAR — detects spy cameras that transmit over Wi-Fi/BLE (or via RF sensor — see unresolved item above), and guides the user toward the source using directional signal-strength tracking.
WIRED CAMERA DETECTOR — detects offline/SD-card spy cameras using the phone's camera and real-time in-browser computer vision to catch the IR LED glow + blink pattern these cameras emit.
EMERGENCY SOS — a GPS-based panic button that sends WhatsApp alerts to a trusted contact.

CURRENT TECH STACK

AS ORIGINALLY BUILT (hackathon version — being migrated away from, see Update Note 1):

Firmware: ESP32 in Arduino/C++, using WiFi.h, WebServer.h, NimBLEDevice.h.
Concurrency: FreeRTOS dual-core split — Core 0 runs a background scanTask (Wi-Fi + BLE scanning), Core 1 runs the WebServer loop. A mutex semaphore (jsonMutex) protects shared JSON strings (wifiJson, bleJson) between cores.
REST endpoints exposed by the ESP32: GET /wifi, GET /ble, GET /pir-status, GET /trigger-whatsapp (and / serving the dashboard HTML).
Dashboard: a single embedded HTML/CSS/JS page (stored via PROGMEM, chunk-streamed to the browser), opened directly in the phone's browser — this is the part being replaced by a standalone installable app.

TARGET STACK (current plan):

Firmware: ESP32 stays Arduino/C++. Keeps sensor-reading logic and exposes results as JSON over Wi-Fi (exact endpoints TBD pending Update Note 2). The dual-core FreeRTOS split (scan/sensor task on Core 0, web server on Core 1) likely still makes sense regardless of which sensing approach is used, to avoid blocking the server during a scan/read cycle — carry this pattern forward unless the RF-sensor approach turns out to need it.
Phone app: standalone HTML/CSS/JS project (vanilla, no framework — matches existing style), packaged into an installable Android app via Capacitor. Fetches sensor JSON from the ESP32's IP, runs all client-side logic: direction/gradient-ascent guidance, the wired-detector CV pipeline, SOS/Geolocation, and Green API WhatsApp calls.
The CV pipeline (Section 4), SOS/Geolocation flow (Section 5.1), and Green API alerting (Section 5.2) are UNCHANGED by the platform shift — they're standard browser APIs (getUserMedia, canvas, Geolocation, fetch) that work the same inside a Capacitor WebView as they did in a regular mobile browser. Capacitor plugins (camera, geolocation, motion) may be swapped in later if the plain browser APIs misbehave inside the native wrapper, but this is not required to start.
